# 라벨 일급 객체 파이프라인 — 유스케이스와 시나리오

대상 설계: [`02-design.md`](02-design.md)
버전: 0.1 (백엔드 세부 설계 착수용)

이 문서는 [`02-design.md`](02-design.md)가 정의한 데이터 모델·알고리즘을 **누가, 언제, 어떤
순서로 호출하는가**로 바꿔 적는다. 세부 설계([`04-backend-design.md`](04-backend-design.md))는
여기서 도출된 유스케이스와 경계 케이스만을 근거로 범위를 결정한다. 여기에 없는 요구는 설계하지
않는다.

## 1. 액터

| 액터 | 종류 | 관심사 |
|------|------|--------|
| 파이프라인 운영자 (Ops) | 사람 | 배치 실행, 실패 재개, 비용 상한, 라벨러 활성/격리 |

그들과 **계약(API)** 으로만 만난다.

## 4. 유스케이스 상세

상세 서술은 백엔드 계약이 갈리는 8건만 한다. 나머지는 §3 목록과 §5 시나리오로 충분하다.

### UC-01 라벨러 배치 실행

| 항목 | 내용 |
|------|------|
| 주 액터 | 오케스트레이터 (수동 실행 시 Ops) |
| 사전조건 | 태스크 설정이 유효, 라벨러 최소 1개 `enabled`, feature 스냅샷 조회 가능 |
| 사후조건 | 대상 표본 × 활성 라벨러 조합마다 L0 1행, L1 1행(기권·파싱 실패 포함) |

**주 흐름**

1. 오케스트레이터가 `(label_task, 대상 기간)`으로 run 생성을 요청한다.
2. 시스템이 `run_id`를 발급하고, feature 스냅샷 ID를 **그 시점에 고정**한다.
3. 대상 표본 집합을 확정하고 라벨러별 샤드로 분할한다.
4. 라벨러별로 배치를 실행한다. 각 호출마다 L0(원시 응답)를 먼저 적재하고, 파싱 결과를 L1으로 적재한다.
5. 모든 샤드 종료 후 run을 `committed`로 전이하고, 적재 행 수·비용·소요 시간을 기록한다.

**대안 흐름**

- 1a. 동일 `(label_task, 기간, 설정 해시)`의 run이 이미 존재 → 기존 `run_id`를 반환하고 신규 생성하지 않는다(멱등).
- 4a. 캐시 적중(`inputs_hash + method_ver + prompt_hash + params_hash`) → 외부 호출을 생략하고 캐시 출처를 L0에 명시한다. 앵커 재채점 경로에서는 캐시를 사용하지 않는다(§12.3).
- 4b. 파싱 실패 → L1을 `parse_status='failed'`로 적재한다. 행을 버리지 않는다.
- 4c. 라벨러가 판단을 유보 → `is_abstain=true`. `value_*`는 NULL이지만 이는 결측이 아니라 관측이다(P3).

**예외 흐름**

- 4x. 429/5xx → 지수 백오프 최대 4회. 소진 시 해당 표본을 실패로 기록하고 샤드는 계속 진행한다.
- 4y. run 누적 비용이 `max_cost_usd_per_run` 초과 → 신규 호출을 차단하고 이미 성공한 분량을 커밋한 뒤 run을 `partially_failed`로 전이한다.
- 4z. 워커 프로세스 소실 → 샤드 체크포인트에서 재개(UC-02). 같은 `run_id`를 유지하므로 중복 적재는 PK 충돌로 흡수된다(§12.1).

**수용 기준**: 동일 `run_id`로 2회 실행해도 L1 행 수가 변하지 않는다.

### UC-02 실패한 run 재개

| 항목 | 내용 |
|------|------|
| 사전조건 | run 상태가 `partially_failed` |
| 사후조건 | 실패 샤드만 재실행되고 run이 `committed`로 전이 |

주 흐름: Ops가 재개를 요청 → 시스템이 미완 샤드 목록을 계산 → **같은 `run_id`, 같은 feature
스냅샷 ID**로 재실행 → 성공 시 커밋.

예외: 비용 상한 때문에 중단된 run은 상한을 상향 조정하지 않으면 재개가 즉시 다시 차단된다.
상한 변경은 설정 변경이므로 새 `config_hash`를 만들고, 그 사실을 run 메타에 남긴다.

### UC-04 합의 산출 (L2 발행)

| 항목 | 내용 |
|------|------|
| 사전조건 | 대상 태스크의 L1이 존재, `fusion_policy_ver`·보정 모델 버전이 확정 |
| 사후조건 | 대상 키마다 L2 1행(`l2_version` 부여), 불일치 표본은 검수 큐에 적재 |

**주 흐름**

1. `(label_task, ontology_ver)` 단위로 fusion 실행을 요청한다.
2. `v_l1_latest`(또는 지정 `run_id` 집합)에서 후보를 읽는다.
3. 보정 → 상관 보정 → 가중 투표 → 라우팅 순으로 계산한다(§7.2).
4. L2를 `l2_version + 1`로 발행하고, 입력 `run_id`/`label_id` 목록과 정책 버전을 함께 기록한다.
5. `flag='pending_review'` 또는 `no_signal`인 키를 검수 큐에 enqueue한다.

**대안 흐름**

- 2a. 후보가 모두 기권 → `flag='no_signal'`, 낮은 우선순위로 큐에 적재. `value`는 NULL이지만 행은 생성한다.
- 3a. 보정 모델의 학습 표본이 `n_min` 미만 → 항등 사상 + 균등 가중으로 폴백하고, 그 사실을 L2 메타에 남긴다(부트스트랩 경로, §8.2).
- 5a. 동일 키가 이미 `queued`/`assigned` 상태로 큐에 있음 → 중복 enqueue하지 않고 우선순위만 갱신한다.

**예외 흐름**

- 2x. 후보의 `ontology_ver`가 섞여 있음 → 혼합 합의는 금지(§6). 목표 버전으로 사상 가능한 후보만 투입하고, 사상 불가(`split`)는 큐로 우회시킨다.
- 4x. 동일 태스크의 fusion이 이미 실행 중 → 두 번째 요청은 거절한다. 같은 키에 두 개의 `l2_version`이 경쟁 생성되면 매니페스트가 가리키는 버전이 모호해진다.

**수용 기준**: 골든 픽스처 입력에 대해 L2 출력이 바이트 단위로 일치한다. `pending_review`에도
`value`가 채워져 있다(P4).

### UC-05 검수 과제 배정과 제출

| 항목 | 내용 |
|------|------|
| 주 액터 | 검수자 (검수 플랫폼 경유) |
| 사전조건 | 검수 큐에 `queued` 과제 존재, 검수자 권한 확인 |
| 사후조건 | L3 1행 적재, 큐 항목 `done`, 해당 키의 L2가 `human_final`로 갱신(UC-15) |

**주 흐름**

1. 검수 플랫폼이 과제 N건을 요청한다.
2. 시스템이 우선순위 순으로 N건을 선택해 **임대(lease)** 를 부여하고 `assigned`로 전이한다.
3. 검수자가 판정 결과를 제출한다.
4. 시스템이 L3를 적재한다. `l3_purpose`는 `hash(sample_id || label_task) mod 100 < holdout_pct`로 결정론적으로 배정한다.
5. 큐 항목을 `done`으로 전이하고, 검수 비용·소요 시간을 기록한다.

**대안 흐름**

- 2a. 앵커 경로 과제는 우선순위와 무관하게 예산 비율 `ρ`만큼 강제 배정한다(P5). 불일치 과제가 아무리 많아도 앵커 몫을 잠식하지 않는다.
- 2b. 이중 검수 대상(앵커의 20%)은 서로 다른 두 검수자에게 배정한다. 같은 검수자에게 두 번 배정되지 않는다.
- 3a. 판정 불가 제출 → `is_abstain`으로 기록하고 큐를 중재(`escalation`) 경로로 전이한다.

**예외 흐름**

- 2x. 임대 시간 초과 → 과제를 `queued`로 되돌리고 임대 횟수를 증가시킨다. 반복 만료 시 우선순위를 낮춰 큐 선두를 막지 않게 한다.
- 3x. 동일 과제에 대한 중복 제출(네트워크 재시도) → 멱등 키로 흡수하고 첫 제출을 유지한다. 두 제출의 내용이 다르면 충돌로 거절하고 수동 처리로 넘긴다.
- 3y. 만료된 임대에 대한 뒤늦은 제출 → 해당 과제가 이미 다른 검수자에게 완료되었으면 거절, 아직 미완이면 수용한다.
- 4x. L3 적재는 성공했으나 큐 전이가 실패 → 재시도 시 L3는 PK로 중복 제거되고 큐만 전이된다(§12.1).

**수용 기준**: 한 과제가 두 검수자에게 동시에 `assigned` 되지 않는다. 임대 만료 후에도
제출된 L3는 유실되지 않는다.

### UC-06 앵커 집합 추출

주 흐름: 검수 리드가 기간과 예산을 지정 → 시스템이 모집단(불일치 여부와 무관한 전체)에서
`stratum = feature 분위수 × 예측 클래스`로 층화 추출 → `anchor_set`에 고정 기록 → 큐에
`random_anchor` 경로로 적재.

- `ρ = 0` 설정은 거절한다(P5). 설정 검증 단계에서 막는다.
- 재추출은 `seed = hash(anchor_set_id)`로 동일 결과를 낸다.
- 갱신 시 직전 집합과 `overlap_ratio`만큼 표본을 공유해 비교 가능성을 유지하고, 구 집합에
  `superseded_by`를 기록한다. 구 집합을 삭제하지 않는다.

### UC-08 드리프트 판정과 조치

주 흐름: 일 1회 실행 → 신호 1(PSI, 버킷별 최소 표본 수 충족분만, BH 보정) 계산 → 신호 2(앵커
부분표본 재채점, 캐시 비활성) 계산 → §10.3 표의 4분면으로 판정 → 조치 기록.

- `labeler_drift` 판정 시 자동 조치는 **라벨러 격리 + republish 후보 등록**까지다. republish
  자체는 Ops 승인을 요구한다(UC-14). 자동 재발행은 진행 중인 실험을 흔든다.
- 앵커 재채점은 외부 API 비용을 쓴다. run 비용 상한과 동일한 회로 차단기를 적용한다.
- 표본 부족으로 산출 불가한 버킷은 "안정"이 아니라 **미산출**로 기록한다. 둘을 같게 다루면
  드리프트를 놓친다.

### UC-09 데이터셋 매니페스트 생성·빌드

| 항목 | 내용 |
|------|------|
| 주 액터 | ML 엔지니어 |
| 사전조건 | 대상 L2 버전이 발행 완료, 필터 조건이 유효한 SQL |
| 사후조건 | `dataset_manifest` 1행 + 빌드 결과의 `content_hash` 기록 |

**주 흐름**: 필터·보류 표본 정책을 지정 → 시스템이 feature 스냅샷 ID와 L2/L3 버전을 **고정**
→ 빌드 실행 → 행 수·클래스 분포·배제 건수와 사유별 내역을 계산 → `content_hash`와 함께 매니페스트
적재.

**대안 흐름**

- 보류 표본 정책 3종(배제 / 소프트 라벨 가중 포함 / 전량 포함)을 선택지로 노출한다. 무엇을
  택하든 **배제 건수와 사유는 반드시 기록**한다(P4).
- 진행 중인 fusion이 있는 태스크 → 빌드는 현재 발행된 최신 `l2_version`을 고정해 진행한다.
  발행 중인 버전을 기다리지 않는다.

**예외 흐름**

- 필터가 holdout L3를 참조 → 거절한다(§4.5).
- feature 스냅샷이 보존 기간을 넘겨 소멸 → 빌드를 거절하고 스냅샷 부재를 명시한다. 조용히
  최신 스냅샷으로 대체하지 않는다.

**수용 기준**: 동일 매니페스트로 2회 빌드 시 `content_hash`가 일치한다.

### UC-11 라벨 재생과 계보 조회

주 흐름: 감사자가 `label_id` 지정 → L1 조회 → L0 원시 응답 조회 → feature 스냅샷에서 입력 복원
→ `inputs_hash` 검증 → 현재 파서로 재파싱 → 원본과 diff 반환. 외부 API 호출은 0회다.

- 계보 조회는 역방향도 지원한다: `dataset_id` → L2 버전 → 입력 L1 → 라벨러·정책 버전 →
  feature 스냅샷.
- `inputs_hash` 불일치는 실패가 아니라 **발견**이다. 스냅샷 소멸, `input_spec` 변경, 정규화
  규칙 변경 중 무엇인지 구분해 보고한다.

### UC-13 온톨로지 개정 적용

주 흐름: Ops가 `from_ver → to_ver` 마이그레이션 맵을 등록 → 시스템이 `kind`별로 처리
(`identity`/`rename`/`merge`는 읽기 시점 뷰 사상, `split`은 해당 표본을 `pending_review`로
재라우팅, `drop`은 학습 제외 + 매니페스트에 건수 기록) → 신규 fusion부터 `to_ver` 적용.

- L1은 불변이므로 **원본을 고쳐 쓰지 않는다**(P1). 사상은 뷰에서만 일어난다.
- 개정 시점에 진행 중인 run은 구 버전으로 완주시킨다. 중간에 버전을 바꾸면 한 run 안에 두
  온톨로지가 섞인다.

## 5. 시나리오

유스케이스를 시간축에 늘어놓은 서사다. 백엔드 설계의 통합 테스트 시나리오와 1:1로 대응시킨다.

### S-1 신규 태스크 부트스트랩 (1~2주)

1. 태스크 설정과 라벨러 2종(rule, LLM)을 등록한다. 보정 모델은 아직 없다.
2. 첫 배치 실행(UC-01). L0/L1이 쌓인다.
3. fusion 실행(UC-04). 보정 표본이 없으므로 **항등 사상 + 균등 가중**으로 동작하고, L2에
   `calibration_model_ver = identity-boot`이 기록된다.
4. 앵커 집합을 추출(UC-06)하고 검수를 시작한다(UC-05). 이 단계의 목적은 학습 라벨이 아니라
   **보정·평가의 기준선 확보**다.
5. L3가 라벨러별 200건을 넘으면 보정 모델을 학습한다(UC-07). 이후 fusion부터 보정이 적용된다.

부트스트랩 구간에서 산출된 L2는 "보정 없음"으로 표시되며, 이 구간의 L2를 쓴 매니페스트는 그
사실을 승계한다.

### S-2 정상 일 배치 (매일)

`02:00` 라벨러 실행(UC-01) → `03:00` fusion(UC-04) → 불일치·앵커 과제 큐 적재 → 업무 시간에
검수(UC-05) → 제출분이 L3로 쌓이고 해당 L2가 `human_final`로 갱신(UC-15) → `04:00` 드리프트
판정(UC-08) → 주 1회 보정 재학습(UC-07).

여기서 백엔드가 감당해야 하는 것은 **겹침**이다. 검수 제출은 fusion 실행 중에도 들어오고,
드리프트 판정은 그 둘이 끝나기 전에 시작될 수 있다.

### S-3 라벨러 드리프트 발생

1. LLM 공급자가 모델을 갱신했고(날짜 고정 ID를 쓰므로 자동 갱신은 아니지만 Ops가 `method_ver`를
   올림), 그 이후 PSI가 상승한다.
2. 앵커 재채점 정확도가 함께 하락한다 → `labeler_drift` 판정(§10.3).
3. 자동 조치로 해당 라벨러를 격리한다. 격리된 라벨러는 다음 run에서 제외되지만 **과거 L1은
   그대로 보존**된다.
4. Ops가 영향 범위(해당 라벨러가 기여한 L2 키 목록)를 조회하고 republish를 승인한다(UC-14).
5. `l2_version + 1`이 발행된다. 기존 매니페스트는 이전 버전을 계속 가리키므로 진행 중인 실험은
   영향을 받지 않는다.

### S-4 실험 재현 요구 (감사)

1. 6개월 전 모델의 학습 데이터셋 `dataset_id`가 주어진다.
2. 매니페스트에서 feature 스냅샷 ID, L2/L3 버전, 정책·보정 버전, 필터를 복원한다.
3. 재빌드하고 `content_hash`를 비교한다(UC-10).
4. 특정 라벨이 왜 그 값이 되었는지 질문이 들어오면 L2의 `agreement` 구조체에서 라벨러별 값·
   보정 신뢰도·가중치를 보이고, 필요하면 L0까지 내려가 원시 응답을 제시한다(UC-11).

이 시나리오가 성립하려면 스냅샷 보존 기간 설정(§5.3)이 730일로 유지되어야 한다. 기본값으로
운영하면 여기서 실패한다.

### S-5 라벨러 교체 회귀 검증

1. 프롬프트를 v3 → v4로 바꾼다. 새 `prompt_template_hash`, 새 `method_ver`.
2. **앵커 집합에서만** 신규 버전을 실행한다(전량 재실행 아님).
3. 앵커 정확도를 구 버전과 비교한다. 비열화(신뢰구간 기준)를 통과하지 못하면 배포를 막는다(§9.5).
4. 통과 시 신규 버전을 활성화한다. 구 버전 L1은 보존되므로 사후 비교가 가능하다.

### S-6 파서 변경 영향 평가

JSON 파서의 필드 추출 규칙을 고친다. 전량 replay(UC-11)로 "몇 건이 어떻게 바뀌는가"를 외부
호출 0회로 산출한다. 변경 영향이 허용 범위면 새 `schema_ver`로 L1을 재적재한다(구 L1은 유지,
`v_l1_latest`가 신규본을 노출).

## 6. 경계 케이스 목록

백엔드가 반드시 답을 가져야 하는 상황이다. "설계안에는 적혀 있지 않지만 코드는 반드시 무언가를
하게 되는" 지점만 골랐다.

| ID | 상황 | 기대 동작 | 근거 |
|----|------|-----------|------|
| EC-01 | 동일 run 요청이 중복 도착 | 기존 `run_id` 반환, 신규 생성 없음 | §12.1 |
| EC-02 | 같은 태스크에 대해 fusion 2건 동시 실행 | 두 번째 거절 (태스크 단위 배타 락) | §7.1 |
| EC-03 | run 도중 feature 테이블이 갱신됨 | run 시작 시 고정한 스냅샷 ID로 끝까지 진행 | §5.3 |
| EC-04 | 라벨러가 응답했으나 JSON 파싱 실패 | L0 보존 + L1 `parse_status='failed'` 적재, `v_l1_latest`에서 제외 | §12.2 |
| EC-05 | 모든 라벨러가 기권 | L2 `no_signal` 행 생성, 낮은 우선순위로 큐 적재 | §7.2 |
| EC-06 | 비용 상한 도달 | 신규 호출 차단, 성공분 커밋, `partially_failed` | §12.3 |
| EC-07 | 검수 임대 만료 후 뒤늦은 제출 | 미완이면 수용, 이미 완료면 거절 | §9 |
| EC-08 | 동일 과제 중복 제출 | 멱등 키로 첫 제출 유지, 내용 상이 시 충돌 거절 | §12.1 |
| EC-09 | 검수자 2인이 서로 다른 판정 | `escalation` 경로로 3인째 중재, `adjudicated=true` | §9.4 |
| EC-10 | L3 적재 성공 + 큐 전이 실패 | 재시도 시 L3 중복 제거, 큐만 전이 | §12.1 |
| EC-11 | 불일치 과제가 예산을 잠식 | 앵커 몫 `ρ`는 선점 불가 | §9.1 (P5) |
| EC-12 | `ρ = 0` 설정 시도 | 설정 검증에서 거절 | §14.4 |
| EC-13 | fusion이 holdout L3를 참조하려 함 | 코드 경로 정적 검사 + 런타임 뷰 강제로 차단 | §4.5 |
| EC-14 | 보정 학습 표본 부족 | 항등 사상 폴백, 그 사실을 L2에 기록 | §8.2 |
| EC-15 | 라벨러 2개가 동일 기반 모델 | 상관 보정으로 가중치 축소 | §7.3 |
| EC-16 | PSI 산출 버킷의 표본 부족 | "안정"이 아니라 "미산출"로 기록 | §10.1 |
| EC-17 | 드리프트 판정이 republish를 유발 | 자동 격리까지만, republish는 승인 필요 | §10.4 |
| EC-18 | 매니페스트가 참조한 스냅샷 소멸 | 빌드 거절, 대체 금지 | §5.3 |
| EC-19 | 온톨로지 `split` 발생 | 해당 표본 `pending_review` 재라우팅 | §6 |
| EC-20 | 외부 전송 라벨러를 민감 태스크에 배정 | 정책 검증에서 거절 | §14.3 |
| EC-21 | 지연 L3가 이미 발행된 매니페스트 대상 표본에 도착 | 새 `l2_version` 생성, 기존 매니페스트는 불변 | §12.4 |
| EC-22 | 워커 소실 후 재기동 | 샤드 체크포인트에서 재개, 같은 `run_id` 유지 | §12.2 |

## 7. 비기능 요구 (가정)

실측 전이므로 **가정임을 명시**한다. 세부 설계는 이 수치를 설계 상수가 아니라 설정값으로 다룬다.

| 항목 | 가정 | 근거/영향 |
|------|------|-----------|
| 일 신규 표본 | 5만 건 | L1 = 5만 × 라벨러 3 = 15만 행/일 |
| 라벨러 수 | 태스크당 2~4 | 상관 보정이 의미를 갖는 최소 규모 |
| 일 배치 소요 | 2시간 이내 | LLM 동시성 8, 200k TPM 상한 |
| 검수 예산 | 주기당 500건 | 앵커 75건(ρ=0.15), 중재 25건 |
| 동시 검수자 | 10~30명 | 큐 API는 초당 수 건 수준. 고QPS 설계 불필요 |
| 제어 API QPS | < 50 | 단일 인스턴스로 충분. 수평 확장은 무상태성만 확보 |
| 데이터셋 빌드 | 10분 이내 | 배치 잡, 동기 응답 아님 |
| 가용성 | 업무시간 99% | 배치 파이프라인. 초 단위 SLA 없음 |

이 규모에서는 마이크로서비스 분할·전용 메시지 브로커·실시간 스트리밍이 필요하지 않다. 세부
설계가 그 방향으로 가면 과설계다.
