## 요 약

인공지능 모델의 성능은 학습 데이터의 품질뿐 아니라 라벨의 정확성과 일관성에 크게 좌우된다.
실무 환경에서는 규칙 기반 라벨러, 대규모 언어 모델(LLM) 기반 라벨러, 사람 검수 등 다양한
라벨링 방식이 동시에 운용되며, 라벨 자체가 파이프라인의 산출물로 취급되어야 한다. 라벨 메타
관리의 중요성은 Snorkel 등 약지도 학습 프레임워크와 Label Studio·Encord 등 라벨링
플랫폼에서 부분적으로 다루어져 왔으나, 라벨이 자체 시스템 내부의 격리된 객체로 관리되어
데이터 레이크의 feature 데이터와 동일한 저장·계층·계보 인프라를 공유하지 못하는 한계가 있다.
본 논문은 라벨을 데이터 레이크의 일급 객체(first-class citizen)로 통합 관리하는 데이터
파이프라인 설계를 제안한다. 제안 설계는 (i) 이종 라벨러(rule/LLM/human)를 기권(abstain)과
라벨 대상 단위까지 포함해 통합 표현하는 라벨 객체 스키마, (ii) 라벨러의 원시 응답과 후보
출력(L1)을 폐기하지 않고 각각 Bronze·Silver 계층에 영구 보존하여 합의 라벨(L2)·검증
라벨(L3)과 함께 **재생(replay) 가능성**을 확보하는 저장 전략, (iii) 라벨러별 신뢰도 보정과
상관 보정을 거쳐 불일치를 검수 경로로 라우팅하는 Label Fusion Engine, (iv) feature 스냅샷과
라벨 버전을 묶어 학습 시점을 고정하는 데이터셋 매니페스트로 구성된다. 특히 검수 예산의 일부를
무작위 표본에 강제 배정하는 앵커 집합(anchor set)을 도입하여, 불일치 표본에만 의존하는
기존 검수 전략이 라벨러 평가와 드리프트 감지에 유발하는 편향을 제거한다.

## 1. 서 론

최근 다양한 산업에서 인공지능 기반 의사결정 시스템이 도입되면서, 모델 학습에 필요한 라벨링
데이터의 확보와 관리가 핵심 과제가 되고 있다. 특히 재난 안전, 의료, 금융 등 전문 도메인에서는
대량의 고품질 라벨을 확보하기 어려워 약지도 학습(weak supervision)과 대규모 언어 모델(LLM)을
활용한 자동 라벨링 방식이 확산되고 있다[1].

그러나 실무 파이프라인에서 라벨은 더 이상 외부에서 주어진 고정 입력이 아니다. 규칙 엔진, LLM,
사람 검수가 동시에 라벨을 생성하며, 각 방식은 서로 다른 품질·비용·지연 특성을 가진다. 규칙
기반 라벨러는 해석 가능하고 재현성이 높으나 경계 사례(edge case)를 놓치기 쉽고, LLM 기반
라벨러는 맥락 이해에 강점이 있으나 모델 버전·프롬프트 변경에 따른 드리프트와 비결정성 문제가
있다[2]. 이러한 다중 라벨러의 공존은 "라벨을 어떻게 저장·관리·추적할 것인가"라는 데이터
엔지니어링 과제를 낳고 있다.

라벨 관리의 중요성은 일찍이 인식되어, Snorkel[1]은 다중 라벨링 함수의 출력을 통합하면서 각
라벨의 계보(lineage)를 확률적으로 모델링하였고, Label Studio·Encord 등 산업용 라벨링
플랫폼은 라벨러 ID·생성 시각·모델 버전 등의 메타와 감사 이력(audit trail)을 지원하고 있다.
그러나 이러한 도구들은 공통적으로 라벨을 자체 시스템 내부에서 격리된 객체로 관리한다. 그 결과,
라벨이 데이터 레이크에 저장된 feature 데이터와 동일한 저장·계층·계보 인프라를 공유하지 못하며,
학습 데이터셋 구성 시점에 별도의 익스포트·통합 단계를 거쳐야 한다. 또한 대부분의 시스템은 합의
또는 최종 라벨만을 학습용으로 노출하고, 라벨러별 후보 출력은 임시 저장 또는 내부 텐서로만
유지되어 사후 분석이나 라벨러 회귀 검증이 어렵다.

본 논문은 라벨을 데이터 레이크의 일급 객체로 승격시켜 feature 데이터와 동등한 저장·계층·계보
인프라 위에서 관리하는 데이터 파이프라인을 제안한다. 주요 기여는 다음과 같다.

1. **일급 객체 조건의 조작적 정의와 통합 라벨 객체 스키마.** "라벨이 일급 객체이다"를 검증
   가능한 7개 조건으로 정의하고(3.1), rule/LLM/human 라벨러를 동일 추상으로 표현하되 기권,
   라벨 대상 단위, 온톨로지 버전까지 포섭하는 스키마를 제시한다(3.2).
2. **재생 가능성을 보장하는 4계층 저장 전략.** 라벨러의 원시 응답을 Bronze에, 파싱·검증된
   후보 라벨(L1)을 Silver에 영구 보존하고, 정규화된 해시 규격과 feature 스냅샷 식별자를 통해
   비결정적 라벨러에 대해서도 사후 재생을 가능케 한다(3.3, 3.4).
3. **보정 기반 Label Fusion Engine.** 라벨러 간 비교 불가능한 신뢰도를 앵커 기반으로
   보정하고, 라벨러 상관을 반영한 가중 합의를 수행하며, 불일치 표본을 검수 경로로 라우팅하되
   보류 표본을 학습 데이터에서 무조건 배제하지 않음으로써 선택 편향을 통제한다(3.5, 3.6).
4. **앵커 집합과 데이터셋 매니페스트.** 검수 예산의 일부를 무작위 표본에 강제 배정해 라벨러
   평가·드리프트 감지의 기준선을 확보하고(3.6, 3.7), feature 스냅샷·라벨 버전·합의 정책
   버전을 하나의 객체로 묶어 학습 시점을 재현한다(3.8).

## 2. 관련연구

### 2.1 약지도 학습과 프로그램적 라벨링

Snorkel[1]은 다수의 라벨링 함수(labeling function)를 정의하고 그 출력을 확률적 모델로
통합하는 약지도 학습 프레임워크로, 라벨 소스의 정확도와 **상관관계**를 추정하여 가중 합의 라벨을
생성하며 이 과정에서 각 라벨의 계보를 확률적으로 모델링한다. 라벨링 함수가 판단을 유보하는
기권(abstain) 출력을 일급으로 취급하는 점도 이 계열의 중요한 설계 요소이다. 이후 Ratner
등[4]은 다중 작업 설정에서 라벨링 함수 간 의존 구조를 학습하는 방법으로 이를 확장하였다.
최근에는 LLM을 라벨링 함수로 활용하는 LLM-as-Judge[2] 계열 연구가 확산되어, 전문가 수준의
자동 라벨링이 가능해지고 있다.

이들 연구는 라벨링 함수의 합의 알고리즘과 확률적 라벨 생성에 강점을 가지며, Snorkel Flow와
같은 상용 후속 시스템은 Databricks 등 데이터 플랫폼과의 export·import 연동을 제공한다.
그러나 라벨러별 후보 출력이 데이터 레이크의 영속 객체로 저장·재사용되도록 native하게 설계되어
있지는 않으며, 합의 결과는 일반적으로 학습 직전에 텐서 형태로 출력된다. 본 논문은 Snorkel의
상관 보정 및 기권 처리 아이디어를 계승하되, 이를 레이크 테이블 위의 영속 연산으로 재배치한다.

### 2.2 LLM-as-Judge의 신뢰성과 한계

LLM을 판정자 또는 라벨러로 활용하는 패러다임[2]은 대규모 자동 라벨 생성에 적합하지만, 최근
연구는 이 방식의 신뢰성에 대한 체계적 의문을 제기하고 있다. Thakur 등[5]은 여러 LLM 판정자의
사람 선호와의 정렬도(alignment) 및 체계적 취약점을 평가하여, 위치 편향·자기 선호 편향·응답
길이 편향 등 특정 편향 패턴이 반복적으로 발생함을 보였다. LLM-as-Judge의 설계 선택이
신뢰성에 미치는 영향을 분석한 실증 연구[6]는 평가 기준의 명확성이 신뢰성의 가장 큰 변수이며,
비결정적 샘플링이 오히려 사람 선호와의 정렬을 개선할 수 있음을 보고하였다. 또한 Schroeder와
Wood-Doughty[7]는 동일 입력에 대한 LLM 판정의 run-to-run 재현성 문제를 정량화하여, 단일
LLM 라벨러만으로는 안정적인 학습 데이터를 구성하기 어려움을 시사하였다.

이러한 결과는 두 가지를 동시에 함의한다. 첫째, 다중 라벨러의 병렬 운용과 라벨러 간
합의·불일치의 체계적 기록이 필수적이다. 둘째, **LLM 라벨러에 대해 비트 단위 재현(reproduce)을
전제하는 설계는 성립하지 않는다.** 샘플링 파라미터와 seed를 고정하더라도 배치 구성에 따른
수치 비결정성, 서비스 측 모델 갱신 등으로 동일 출력이 보장되지 않기 때문이다. 본 논문은 이
제약을 설계 전제로 수용하여, 재현 대신 원시 응답 보존에 기반한 **재생(replay)** 을 목표로
설정한다(3.3).

### 2.3 라벨링 플랫폼과 라벨 관리 도구

Label Studio[8]는 대표적인 오픈소스 라벨링 플랫폼으로, 라벨 ID·생성 시각·수정 시각·라벨러
식별자·모델 예측 버전 등을 표준 JSON 스키마로 저장한다. Encord·Labelbox·Kili 등 상용
플랫폼은 여기에 더해 다중 라벨러 합의 점수, 검수 워크플로우, 감사 이력, 라벨 온톨로지 버전 관리
기능을 제공한다. 한편 lakeFS[9]와 같은 데이터 버전 관리 도구는 라벨 데이터를 git-like
브랜치·태그로 관리하여 학습 시점의 라벨 상태를 재현할 수 있게 해준다.

이러한 도구들은 라벨 관리에 필요한 핵심 메타와 감사 기능을 충실히 갖추고 있으나, 라벨을 자체
플랫폼 내부에 저장하여 외부 데이터 레이크의 feature 데이터와 분리된 사일로(silo)를 형성한다.
학습 데이터셋 구성 시 별도의 익스포트·조인 과정이 필요하고, 라벨과 feature가 서로 다른
계보·품질 관리 체계를 가지게 되어 통합적 추적성이 저해된다. 본 논문은 이러한 분리를 해소하기
위해 라벨을 데이터 레이크 native 객체로 정의하는 접근을 취한다.

## 3. 제안연구

본 논문은 라벨을 일급 객체로 취급하는 메달리온[3] 기반 데이터 파이프라인을 제안한다.

### 3.1 일급 객체의 조작적 정의

"일급 객체"는 시스템 내에서 고유 정체성·스키마·수명주기를 가지고 다른 객체와 동등하게 취급되는
요소를 의미한다. 본 논문은 이 개념을 검증 가능한 형태로 조작화하여, 라벨이 다음 7개 조건을
모두 만족할 때 데이터 레이크의 일급 객체라고 정의한다. 표 1은 각 조건과 기존 도구의 충족
여부를 정리한 것이다.

**표 1. 라벨의 일급 객체 조건과 기존 도구 대비**

| # | 조건 | 구현 형태 | 기존 라벨링 플랫폼 |
|---|------|-----------|-------------------|
| C1 | 독립 식별자 | 라벨 PK가 feature 행에 종속되지 않음 | 부분 충족 |
| C2 | 독립 스키마와 진화 | 카탈로그 등록 테이블, schema evolution | 플랫폼 내부 JSON |
| C3 | 독립 수명주기 | 라벨만 별도 버전·롤백·보존 정책 | 미충족 |
| C4 | 동일 계보 그래프 | feature와 같은 lineage 시스템의 노드 | **미충족** |
| C5 | 동일 품질 게이트 | feature와 같은 데이터 품질 검증 체계 | 미충족 |
| C6 | 동일 접근 통제 | 카탈로그 권한 체계 공유 | 미충족 |
| C7 | 표준 질의 가능 | export 없이 SQL로 feature와 직접 조인 | **미충족** |

제안 설계의 기여는 C4와 C7을 충족시키는 데 있으며, 3.2~3.8의 각 구성요소는 이 조건들에
대응한다.

### 3.2 구조화된 라벨 객체 스키마

기존 파이프라인에서 라벨은 단일 스칼라 컬럼으로 저장되어, "누가·언제·어떤 방식으로 이 라벨을
생성했는가"에 대한 정보가 유실된다. 본 논문에서는 라벨을 표 2의 필드를 갖는 구조화된 객체로
정의한다. 초고의 스키마와 비교하여 식별·대상·기권·실행 메타가 추가되었으며, 그 필요성은
3.5~3.8에서 각각 설명한다.

**표 2. 후보 라벨(L1) 객체 스키마**

| 그룹 | 필드 | 설명 |
|------|------|------|
| 식별 | `sample_id` | 라벨 대상 샘플 식별자 (feature 테이블 조인 키) |
| | `label_task` | 태스크 식별자. 한 샘플에 복수 태스크가 공존할 수 있음 |
| | `target_ref` | 라벨 적용 범위 (문서 전체 / 문자 오프셋 / 바운딩 박스) |
| | `ontology_ver` | 클래스 체계 버전 |
| 값 | `value_type` | `class` / `numeric` / `multilabel` 판별자 |
| | `value_class`, `value_num`, `value_json` | 타입별 라벨 값 |
| | `is_abstain` | 기권 여부. "판단 유보"와 "부정 라벨"의 구분 |
| 라벨러 | `method` | 라벨러 유형 (rule / llm / human / hybrid) |
| | `method_ver` | 라벨러 버전 식별자 (예: `rule-v2.1`, 날짜 고정 모델 ID) |
| | `labeler_id` | 라벨러 인스턴스 식별자 |
| | `prompt_hash`, `params_hash`, `retrieval_ctx_hash` | LLM 라벨러의 프롬프트·샘플링 파라미터·검색 컨텍스트 해시 |
| 신뢰도 | `confidence_raw` | 라벨러가 보고한 원 신뢰도 |
| | `confidence` | 앵커 기반 보정을 거친 신뢰도 ∈ [0, 1] |
| 근거 | `rationale_ref` | 라벨 근거(규칙명, LLM 설명, 검수자 코멘트)에 대한 참조 |
| 재생 | `inputs_hash` | 정규화 규격에 따른 입력 feature 해시 |
| | `feature_snapshot_id` | 입력 feature 테이블의 스냅샷/버전 식별자 |
| | `raw_response_ref` | Bronze에 적재된 원시 응답에 대한 참조 |
| 실행 | `run_id` | 라벨링 실행 식별자 (재실행분 구분, 멱등성 키) |
| | `labeled_at` | 라벨 생성 시각 |
| | `cost`, `latency_ms`, `token_usage` | 비용·지연 측정용 |

기본 키는 `(sample_id, label_task, target_ref, labeler_id, run_id)`이다.

이 스키마의 핵심은 `method`와 `method_ver` 필드를 통해 라벨러 유형의 차이를 메타로 흡수한다는
점이다. 규칙 라벨러의 규칙 ID, LLM의 모델 버전, 사람 검수자의 식별자가 모두 동일 필드에
정규화되어 저장되므로, 학습 단계에서 라벨러별 분리·비교·교체가 데이터 레이크의 표준 메타
질의만으로 가능하며, 외부 라벨링 시스템에 의존하지 않는다(C7).

초고에서 L1 스키마에 포함되었던 `agreement`(다중 라벨러 raw 결과의 구조화 기록) 필드는
개별 후보 라벨이 보유할 수 없는 정보이므로 L2 스키마로 이동하였다. 이로써 L1은 append-only
불변 레코드로 유지되며, 라벨러 실행 시점에 다른 라벨러의 결과를 알아야 하는 순환 의존이
제거된다. L2와 L3의 스키마는 [`02-design.md`](02-design.md) 4장에 정의한다.

### 3.3 정규화 해시와 재생(replay) 가능성

재현성의 근거가 되는 `inputs_hash`는 직렬화 방식이 흔들리면 같은 입력에서도 다른 값을 내므로,
다음 정규화 규격을 강제한다. (i) UTF-8 NFC 정규화, (ii) 객체 키를 코드포인트 순 정렬,
(iii) 공백 없는 JSON 직렬화, (iv) 부동소수는 유효숫자 12자리에서 짝수 반올림, (v) 결측은
JSON `null`로 통일. 해시 대상은 전체 feature가 아니라 **해당 라벨러가 선언한 입력
명세(input spec)** 로 한정하여, 무관한 컬럼 변경이 해시를 바꾸지 않도록 한다.

한편 해시만으로는 입력을 복원할 수 없으므로 `feature_snapshot_id`(Delta version 또는
Iceberg snapshot id)를 함께 저장하여 시점 이동(time travel)으로 실제 입력을 되살릴 수 있게
한다. 이때 테이블의 스냅샷 보존 기간이 기본값으로 운용되면 시점 이동이 조용히 실패하므로, 라벨이
참조하는 feature 테이블은 보존 기간을 라벨 보존 정책에 맞추어 확대 설정해야 한다.

결정론적 라벨러(rule)는 동일 `inputs_hash`·`method_ver`에서 동일 값을 재생성하므로 완전
재현이 성립한다. 반면 LLM 라벨러는 2.2에서 논의한 바와 같이 seed 고정으로도 재현이 보장되지
않는다. 따라서 본 설계는 LLM 라벨러에 대해 재현 대신 **재생(replay)** 을 목표로 한다. 즉
라벨러의 원시 응답 전문을 Bronze 계층에 보존하여, 파싱·검증 로직이 변경되더라도 외부 API를 다시
호출하지 않고 L1을 재생성할 수 있게 한다. `method_ver`에는 별칭(alias) 대신 날짜가 고정된
모델 식별자만 허용하며, 스키마 수준 검증으로 이를 강제한다.

### 3.4 4계층 매핑

제안 구조는 라벨을 메달리온 아키텍처의 네 계층에 매핑한다(그림 1).

**[그림 1. 메달리온 기반 라벨 관리 파이프라인]**

- **L0 원시 응답(Bronze).** LLM API 응답 전문, 규칙 엔진의 원시 평가 로그, 검수 UI의
  이벤트 로그. 파싱 이전 상태로 보존되어 L1 재생의 근거가 된다.
- **L1 후보 라벨(Silver).** 각 라벨러의 파싱·스키마 검증을 통과한 출력이다. 여러 라벨러가
  병렬로 실행되어 동일 샘플에 대해 복수의 L1이 생성되며, append-only로 적재된다.
- **L2 합의 라벨(Gold).** 후보 라벨들을 합의 정책에 따라 통합한 결과이다. 학습 데이터의 기본
  라벨로 사용된다.
- **L3 검증 라벨(Gold, 별도 파티션).** 사람 검수를 통과한 일부 샘플의 라벨이다. 라벨러 정확도
  평가와 드리프트 감지의 앵커로 활용된다.

초고는 라벨러의 원시 출력을 Silver에 두었으나, Silver의 통상적 정의(정제·정합화 계층)와의
충돌을 피하고 재생 경로를 명시하기 위해 원시 응답(L0)과 검증된 후보(L1)를 분리하였다.

### 3.5 Label Fusion Engine

Label Fusion Engine은 L1 후보 라벨들을 L2 합의 라벨로 변환하고, 라벨러 간 불일치를 사람 검수
경로로 라우팅하는 컴포넌트이다. 동작은 알고리즘 1과 같다.

**알고리즘 1. Label Fusion Engine**

```
입력: 샘플 x, 태스크 t, 후보 집합 C, 보정 함수 g, 상관 행렬 Σ,
      합의 정책 P(버전 fusion_policy_ver), 임계값 θ

1  A ← {c ∈ C : ¬c.is_abstain}                    # 기권 제외
2  if |A| = 0:
3      emit L2 ← {value: NULL, flag: "no_signal"}
4      enqueue(x, t, priority = LOW);  return
5  for c ∈ A:  c.conf ← g[c.labeler_id](c.confidence_raw)   # 신뢰도 보정
6  w ← correlation_adjusted_weights(A, Σ)          # 라벨러 상관 보정
7  p ← normalize( Σ_{c∈A} w_c · c.conf · onehot(c.value) )  # 클래스별 사후 점수
8  v* ← argmax p ;  margin ← p[v*] − max_{v≠v*} p[v]
9  if unanimous(A):            flag ← "agreed"
10 elif margin ≥ θ:            flag ← "soft_disagreement"
11 else:
12     flag ← "pending_review"
13     enqueue(x, t, priority = f(margin, class_rarity, review_cost))
14 emit L2 ← {value: v*, soft: p, margin, flag, agreement: summarize(A),
              fusion_policy_ver, theta, input_l1_run_ids}
```

초고의 의사코드 대비 네 가지가 달라졌다.

**(a) 기권의 명시적 처리.** 라벨러가 판단을 유보한 출력은 합의에서 제외되며, 모든 라벨러가
기권한 경우는 불일치와 구분되는 `no_signal`로 기록된다.

**(b) 신뢰도 보정(5행).** 초고의 `confidence_gap(L1) > θ` 판정은 rule 라벨러의 고정
신뢰도, LLM의 자기 보고 신뢰도, 검수자의 주관 점수를 동일 축에서 비교한다고 전제하나, 이
전제는 성립하지 않는다. 제안 설계는 3.6의 앵커 집합을 기준으로 라벨러별 단조 보정 함수
(isotonic regression 등)를 학습하여 원 신뢰도를 경험적 정확도로 사상하고, 원값
(`confidence_raw`)과 보정값(`confidence`)을 모두 보존한다. 앵커가 축적되기 전 초기
구간에서는 균등 가중으로 동작하는 부트스트랩 경로를 둔다.

**(c) 라벨러 상관 보정(6행).** 동일 기반 모델을 공유하는 복수의 LLM 라벨러가 존재할 때 단순
다수결은 사실상 한 라벨러에 중복 투표권을 부여한다. L1 이력으로부터 라벨러 쌍의 일치 이력을
추정하여 유효 가중치를 낮추며, 이는 Snorkel[1,4]의 의존 구조 추정을 레이크 테이블 위에서
근사하는 것에 해당한다.

**(d) 보류 표본의 처리(11–14행).** 초고는 불일치 표본의 L2를 NULL로 두었으나, 이 경우 검수가
완료되기 전까지 난이도가 높은 표본만 학습 집합에서 체계적으로 제외되어 선택 편향이 발생한다.
제안 설계는 최선 추정값과 소프트 라벨 분포를 함께 기록하고 `pending_review` 플래그로
표시하며, 학습 집합 포함 여부는 데이터셋 매니페스트(3.8)의 필터 조건으로 명시적으로 선언한다.
이로써 제외된 표본의 규모와 분포가 항상 기록에 남는다.

합의 정책 자체는 교체 가능한 플러그인으로 정의하며, 다수결, 신뢰도 가중 투표, Snorkel 계열
생성 모델을 선택할 수 있다. 다만 Cohen's κ와 같은 일치도 계수는 표본 단위 판정 함수가 아니라
데이터셋 수준의 우연 보정 지표이므로 합의 정책이 아닌 모니터링 지표로 분류한다. 평가자가 3인
이상이고 결측(기권)이 존재하는 본 설정에서는 Krippendorff's α가 적합하다.

L2 레코드는 `fusion_policy_ver`, `theta`, `input_l1_run_ids`를 포함하여, 동일 L1 집합과
동일 정책 버전에서 L2가 결정론적으로 재생성됨을 보장한다.

### 3.6 검수 라우팅과 앵커 집합

불일치 라우팅은 사람 검수 예산을 정보량이 가장 큰 표본에 집중시키므로 라벨링 비용 대비 학습
데이터 품질을 효율적으로 향상시킨다. 그러나 이 전략만 사용하면 L3가 난이도 상위 구간에서만
생성되어, L3를 기준으로 산출한 라벨러 정확도와 드리프트 지표가 모집단을 대표하지 못한다. 또한
검수 결과가 라벨러 개선에 재투입되는 폐루프 구조에서, 개선된 라벨러가 만든 불일치가 다시 검수
대상을 결정하므로 자기강화적 편향이 누적된다.

이를 차단하기 위해 제안 설계는 검수 예산의 일정 비율 ρ(기본 0.15)를 **무작위 표본**에 강제
배정하여 앵커 집합을 구성한다. 앵커 집합은 (i) 라벨러별 신뢰도 보정의 학습 데이터, (ii) 절대
정확도 추정의 기준, (iii) 드리프트 감지의 고정 기준선으로 사용된다.

아울러 검증 라벨은 용도를 `train`과 `eval_holdout`으로 사전 분할한다. 라벨러 평가에 사용된
L3가 합의와 학습에도 투입되면 라벨러 성능이 낙관적으로 추정되기 때문이며, holdout 분할은
Fusion Engine에 노출되지 않는다.

검수 결과(L3)는 규칙 엔진의 규칙 추가와 LLM 프롬프트 회귀 검증에 재투입되어, 라벨러 자체가
점진적으로 개선되는 폐루프(closed loop) 구조를 이룬다.

### 3.7 라벨 드리프트 감지

LLM 라벨러는 모델 업데이트·프롬프트 변경·컨텍스트 변동으로 인해 시간에 따라 판정이 이동할 수
있다. 제안 구조는 두 신호를 병행 관측한다. 첫째, 동일 feature 분위수 구간에서의 L1 분포에 대해
Population Stability Index(PSI) 또는 KL 발산을 주기적으로 계산한다. 둘째, 고정된 무작위
앵커 집합을 주기적으로 재채점하여 절대 정확도의 변화를 추적한다.

단일 신호만으로는 관측된 변화가 라벨러의 판정 이동인지 입력 데이터 분포의 변화인지 식별할 수
없다. 재난 안전 도메인과 같이 사건 발생과 계절성에 따라 입력 분포가 크게 움직이는 환경에서는 이
구분이 특히 중요하다. 제안 설계는 두 신호의 조합으로 원인을 식별한다(표 3).

**표 3. 드리프트 원인 식별 규칙**

| 분포 변화(PSI) | 앵커 정확도 하락 | 해석 | 조치 |
|---|---|---|---|
| 상승 | 없음 | 입력 데이터 드리프트 | 라벨러 유지, feature 모니터링 |
| 상승 | 있음 | 라벨러 드리프트 | 라벨러 버전 점검, 재라벨링 |
| 없음 | 있음 | 점진적 열화 또는 앵커 노후화 | 앵커 갱신 후 재평가 |
| 없음 | 없음 | 안정 | 없음 |

라벨러 드리프트로 판정되어 Gold 계층의 재발행(republish)이 트리거될 경우, 이는 기존 데이터의
덮어쓰기가 아니라 새로운 버전의 생성으로 처리된다. 진행 중인 학습 실험은 3.8의 매니페스트를 통해
특정 버전에 고정되어 있으므로 재발행의 영향을 받지 않는다.

### 3.8 데이터셋 매니페스트

라벨을 일급 객체로 승격시키는 작업은 학습 데이터셋 자체를 식별 가능한 객체로 정의할 때 완결된다.
매니페스트는 `feature_snapshot_id`, `l2_version`, `l3_version`, `fusion_policy_ver`,
`theta`, 학습 집합 필터 조건, 행 수와 클래스 분포를 하나의 레코드로 묶는다. 이를 통해 모델
카드에서 데이터셋, 라벨, 라벨러 버전, feature 스냅샷에 이르는 계보가 끊기지 않고 연결되며,
기존 계보 도구에 라벨이 노드로 등록된다(C4).

---

## 4. 평가 계획

제안 설계의 검증은 두 축으로 구성한다.

**축 1: 합의 품질과 검수 비용.** 비교 대상은 (i) 단일 LLM 라벨러, (ii) 단순 다수결,
(iii) Snorkel 계열 생성 모델, (iv) 전수 사람 검수(상한)이다. 지표는 라벨러 간 일치도
(Krippendorff's α), holdout L3 대비 L2 정확도, 동일 다운스트림 성능 도달까지 소요된 검수
건수, 다운스트림 모델 F1이다.

**축 2: 후보 라벨 영구 보존의 효용.** 이는 제안 설계의 고유 주장이므로 직접 측정한다.
(i) LLM 버전 교체 시 보존된 L1로 수행하는 회귀 분석의 비용과 재호출 방식의 비용 비교,
(ii) 특정 라벨러를 제외했을 때의 L2 변화를 재실행 없이 계산하는 사후 ablation의 가능 여부와
소요 시간, (iii) 이에 소요되는 저장 오버헤드(용량 및 월 비용)와의 손익분기 분석.

---

## 5. 결론

본 논문은 약지도 학습과 LLM 기반 자동 라벨링이 보편화되는 환경에서, 라벨을 데이터 레이크의 일급
객체로 통합 관리하기 위한 데이터 파이프라인을 제안하였다. Snorkel 등 약지도 학습 프레임워크와
Label Studio·Encord 등 라벨링 플랫폼은 이미 라벨 메타와 합의 알고리즘을 지원하지만, 라벨이
자체 시스템 내부에 격리되어 데이터 레이크 인프라와 분리된다는 한계가 있다.

본 연구의 기여는 (i) 일급 객체 조건의 조작적 정의와 기권·대상 단위·온톨로지 버전을 포섭하는
통합 라벨 객체 스키마, (ii) 원시 응답과 후보 라벨을 보존하여 비결정적 라벨러에 대해서도 재생을
보장하는 4계층 매핑, (iii) 신뢰도 보정과 상관 보정을 결합하고 보류 표본의 선택 편향을 통제하는
Label Fusion Engine, (iv) 무작위 앵커 집합에 기반한 드리프트 식별과 데이터셋 매니페스트를 통한
학습 시점 고정에 있다. 이를 통해 라벨이 feature와 동일한 저장·계층·계보 인프라 위에서 관리되며,
기존 메달리온 파이프라인에 점진적으로 통합 가능하다.

향후 연구에서는 실제 재난 안전 도메인 데이터에 제안 구조를 적용하여 4장의 평가 계획을 수행하고,
라벨러 간 합의도와 사람 검수 비용 절감률을 정량적으로 검증할 계획이다.
